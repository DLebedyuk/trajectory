# «Траектория» — контекст проекта

Собрано для переноса в другой разговор. Основной упор — развёртывание.
Состояние на коммит `13965b8`, 58 коммитов всего.

---

## 1. Что это

Личный планировщик Дарьи. Главная идея, из которой растёт вся модель:
**приложение считает пройденное, а не оставшееся**. Отсюда «касания» —
отметки о том, что к направлению вообще прикоснулись, и карта касаний вместо
процентов выполнения.

### Продуктовые инварианты

Их нельзя нарушать при любых правках — они старше любого визуального решения:

- **Задача не существует без проекта, проект — без направления.** Направление
  задачи всегда выводится через её проект, отдельного поля нет.
- **Активная задача одна на всё приложение.** Её направление автоматически
  становится направлением в фокусе. Если выбрать в фокус другое направление
  при живой активной задаче — сервер возвращает 409 и человек сам решает,
  что делать. Молча снять задачу нельзя.
- **Закреплённый проект — один на направление.** На главной показывается тот,
  чьё направление сейчас в фокусе. Меняется фокус — меняется проект. Держится
  частичным уникальным индексом в базе, а не только кодом.
- **Задачи внутри проекта помечаются «важными»**, а не «закреплёнными»:
  слово «закрепить» отдано проектам.
- **ИИ не выдумывает даты.** Если даты нет в тексте — null, и приложение
  спрашивает. Это же правило в промпте и в детерминированном разборе фраз.
- **Ничего не применяется без явного подтверждения.** Разбор входящих — только
  предпросмотр; человек правит и подтверждает.
- **Напоминания — внешняя память, не задачи.** У них нет проекта и приоритета.
  Выполненные лежат в архиве семь дней.
- **Меню возможностей** — приятное и необязательное, без сроков.

### Разделы интерфейса

Главная, Направления (список и страница направления), Проект, Задача,
Напоминания + архив, Меню возможностей, Книги и фильмы (полка), Входящие,
Касания, Активность, Настройки, Архивы задач и касаний.

## 3. Развёртывание на VPS

**Главный документ — `docs/deploy.md` в репозитории.** Здесь то же самое
сжато, чтобы можно было обсуждать, не открывая репозиторий.

### 3.1 Какой сервер нужен

Нагрузка: один активный пользователь плюс 5–10 приглашённых потыкать.

- **2 ГБ памяти, 2 ядра, 20 ГБ диска.** PostgreSQL, API и Caddy вместе
  занимают меньше гигабайта; остальное — запас на сборку образов. Сборка
  образа — самая тяжёлая операция, именно под неё берётся второй гигабайт.
- Ubuntu 22.04 или новее.
- 1 ГБ хватит для работы, но сборка на сервере может упереться в память.
  Если брать 1 ГБ — собирать образы где-то ещё и привозить готовые.

### 3.2 Что нужно до начала

1. Домен с A-записью на IP сервера. Без него Caddy не получит сертификат.
2. Открытые снаружи 80 и 443. Больше ничего открывать не надо.
3. Docker: `curl -fsSL https://get.docker.com | sh`
4. Файрвол:
   ```bash
   sudo ufw allow OpenSSH && sudo ufw allow 80/tcp && sudo ufw allow 443/tcp && sudo ufw enable
   ```
   5432 и 3000 в списке отсутствуют намеренно.

### 3.3 Два compose-файла

| Файл                      | Для чего                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------- |
| `docker-compose.yml`      | локальный стенд на `http://localhost:8080`, публикует наружу postgres:5432 и api:3000 |
| `docker-compose.prod.yml` | VPS: Caddy на 80/443 с HTTPS, база и API портов **не публикуют вовсе**                |

Это **два отдельных файла, а не override**. Причина техническая и важная:
override в compose умеет только добавлять записи в `ports`, но не убирать.
Унаследовав локальный файл, prod выставил бы базу и API в интернет без
возможности это отменить.

### 3.4 Переменные окружения

Полный список валидируется Zod-схемой в `apps/api/src/config/env.ts`.
Для production заполняется `.env.production` (шаблон —
`.env.production.example`, настоящий файл в `.gitignore`).

**Обязательные, без них стенд не поднимется:**

| Переменная                                  | Что это                           | Как получить                            |
| ------------------------------------------- | --------------------------------- | --------------------------------------- |
| `DOMAIN`                                    | публичный домен без схемы         | `planner.example.com`                   |
| `ACME_EMAIL`                                | почта для Let's Encrypt           | своя                                    |
| `POSTGRES_USER` / `POSTGRES_DB`             | имя пользователя и базы           | обычно `planner`                        |
| `POSTGRES_PASSWORD`                         | пароль базы                       | `openssl rand -base64 24`               |
| `SESSION_SECRET`                            | подпись сессий                    | `openssl rand -base64 48`               |
| `TOKEN_ENCRYPTION_KEY`                      | шифрование refresh-токенов Google | `openssl rand -hex 32` — ровно 32 байта |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | вход через Google                 | Google Cloud Console                    |

**Необязательные:**

| Переменная                                               | По умолчанию    | Смысл                                                          |
| -------------------------------------------------------- | --------------- | -------------------------------------------------------------- |
| `TELEGRAM_MODE`                                          | `off`           | `off` / `webhook` / `polling`; на сервере — `webhook`          |
| `TELEGRAM_BOT_TOKEN`                                     | пусто           | от @BotFather                                                  |
| `TELEGRAM_BOT_USERNAME`                                  | пусто           | имя бота без `@`, нужно для deep-link привязки                 |
| `TELEGRAM_WEBHOOK_SECRET`                                | пусто           | **обязателен при webhook**; только латиница, цифры, `-`, `_`   |
| `AI_PROVIDER`                                            | `mock`          | `mock` — разбор правилами, без денег; `openai` — живой платный |
| `AI_API_KEY`, `AI_BASE_URL`, `AI_MODEL`, `AI_TIMEOUT_MS` | —               | нужны только при `openai`                                      |
| `APP_TIMEZONE`                                           | `Europe/Moscow` | часовой пояс по умолчанию                                      |
| `SESSION_TTL_DAYS`                                       | `30`            | срок жизни сессии                                              |
| `RUN_MIGRATIONS`                                         | `true`          | миграции при старте контейнера                                 |

**Прибиты в `docker-compose.prod.yml`, переменной не переопределяются:**
`NODE_ENV=production`, `DEV_AUTH=false`, `RUN_SEED=false`,
`WEB_ORIGIN` / `APP_BASE_URL` / оба `GOOGLE_*_REDIRECT_URI` /
`TELEGRAM_WEBHOOK_URL` — собираются из `DOMAIN`.

### 3.5 Первый запуск

```bash
git clone <репозиторий> planner && cd planner
cp .env.production.example .env.production
nano .env.production

./infrastructure/check-prod-config.sh          # проверка, значений не печатает

docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build
docker compose -f docker-compose.prod.yml --env-file .env.production logs -f web
```

Строка `certificate obtained successfully` в логах web означает, что HTTPS
готов. Первый запуск — несколько минут: собираются образы и выпускается
сертификат.

`check-prod-config.sh` проверяет 23 пункта: заполненность обязательных
переменных, длину секретов, публичность домена, режим Telegram, что наружу
публикуются только 80 и 443, что `NODE_ENV=production` и `DEV_AUTH=false`.
Значений не печатает — только имена и «задано»/«пусто».

### 3.6 Google

В Google Cloud Console → Credentials → OAuth 2.0 Client ID (тип Web),
в «Authorized redirect URIs» **оба** адреса:

```
https://ДОМЕН/api/auth/google/callback
https://ДОМЕН/api/calendar/google/callback
```

Отдельно **включить Google Calendar API** в том же проекте. Если не включить,
Google отвечает 403 `accessNotConfigured`, а приложение показывает доступ
отозванным — эти грабли уже были, на них потеряли время.

Вход и календарь — **разные согласия**. Вход даёт только имя и почту; доступ
к календарю запрашивается отдельно из настроек.

### 3.7 Telegram

`TELEGRAM_MODE=webhook`, токен и секрет в `.env.production`. Адрес вебхука
приложение соберёт само (`https://ДОМЕН/api/telegram/webhook`) и
зарегистрирует при старте — вручную ничего вызывать не надо.

Секрет обязателен: без него ручку вебхука может дёрнуть кто угодно.
Кириллицу Telegram в заголовке не примет — только латиница, цифры, `-`, `_`.

### 3.8 Миграции

Применяются **автоматически при каждом старте контейнера api**
(`apps/api/docker-entrypoint.sh`, `RUN_MIGRATIONS=true`). Вручную — редко:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.production \
  exec api node dist/db/migrate.js
```

Демо-данные в production не загружаются никогда: `RUN_SEED` прибит к `false`.
Откатывать миграции приложение не умеет — перед обновлением с миграцией
нужен дамп.

### 3.9 Резервное копирование

Беречь надо две вещи: том `pgdata` и файл `.env.production`. Без
`TOKEN_ENCRYPTION_KEY` восстановленная база не отдаст токены Google.

```bash
docker compose -f docker-compose.prod.yml --env-file .env.production \
  exec -T postgres pg_dump -U planner -d planner --clean --if-exists \
  | gzip > ~/backup/planner-$(date +%F).sql.gz
```

Ночью по cron — строка есть в `docs/deploy.md` (там же экранирование `%`
и удаление дампов старше двух недель).

**Дамп, который ни разу не разворачивали, — не резервная копия.**

### 3.10 Обновление

```bash
git pull
docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build
```

Пересоберутся только изменившиеся образы, миграции применятся сами.
Откат кода — `git checkout <хеш>` и пересборка; **схема базы при этом не
откатится**, если между версиями была миграция — разворачивать дамп.

`down` останавливает и сохраняет данные. `down -v` сносит тома вместе с базой
и сертификатами — в production эту команду набирать незачем.

### 3.11 Что в production иначе, кроме портов

- `NODE_ENV=production` → кука сессии получает флаг `Secure`. Работает только
  по HTTPS — поэтому локальный стенд намеренно остаётся на `development`.
- `DEV_AUTH=true` в production **запрещён на уровне кода**: приложение не
  стартует, а не пускает всех молча.
- Swagger (`/docs`) закрыт: это карта всего API, включая ручки записи.
- Заголовки безопасности: HSTS, `nosniff`, `X-Frame-Options: DENY`,
  `Referrer-Policy`, скрытый `Server`.
- Сертификаты Caddy лежат в отдельном томе `caddy_data`. Без него каждый
  деплой заново просит сертификат и упирается в лимиты Let's Encrypt.

## 4. Локальная разработка

```bash
pnpm install
docker compose up -d postgres     # или свой PostgreSQL
pnpm db:migrate && pnpm db:seed
pnpm dev                          # api :3000, web :5173
```

Локальный docker-стенд целиком: `docker compose up -d --build` →
`http://localhost:8080`. Redirect URI для него — с портом 8080.

Демо-данные принадлежат seed-пользователю. При настоящем входе через Google
вы попадаете в свой пустой аккаунт и этих данных не увидите — так и задумано.

### Команды

| Команда                                   | Что делает                              |
| ----------------------------------------- | --------------------------------------- |
| `pnpm typecheck`                          | сборка пакетов + `tsc --noEmit` по всем |
| `pnpm lint` / `pnpm format:check`         | ESLint / Prettier                       |
| `pnpm test`                               | все тесты: shared 24, api 187, web 53   |
| `pnpm --filter @planner/api test:audited` | тесты + аудит сетевых попыток           |
| `pnpm build`                              | production-сборка всех пакетов          |
| `pnpm --filter @planner/api smoke:dist`   | дымовая проверка собранного API         |
| `pnpm db:generate`                        | новая миграция из изменений схемы       |

## 5. Тесты

- **shared** — 24: разбор относительных дат, арифметика дат и таймзон.
- **api** — 187 на живой PostgreSQL, 26 файлов. Файлы идут строго по очереди
  (`fileParallelism: false`): делят одну базу.
- **web** — 53, jsdom.

### Изоляция прогона

Важно знать, если будете трогать тесты:

- `apps/api/test/env.setup.ts` выполняется до импортов и **жёстко** выставляет
  `NODE_ENV=test`, `DEV_AUTH=true`, `TELEGRAM_MODE=off`, `AI_PROVIDER=mock`,
  пустой `AI_API_KEY`. Вторым слоем `load-env.ts` при `NODE_ENV=test` вообще
  не читает `.env`. До этого `.env` с `AI_PROVIDER=openai` превращал обычный
  `pnpm test` в платный поход к живому endpoint.
- Там же перехвачен `fetch`: запрос на нелокальный адрес не уходит, а падает
  и пишется в журнал. `pnpm --filter @planner/api test:audited` проверяет
  журнал после всего прогона.
- `prepareDatabase()` делает `TRUNCATE` всех таблиц, поэтому проверяет имя
  базы из `TEST_DATABASE_URL`: оно обязано быть явно тестовым (`planner_test`).
  База `planner` останавливает прогон.

Нужна база `planner_test` на локальном PostgreSQL.

## 6. Что проверено, а что нет

**Проверено** (чистая установка, песочница разработки):

- typecheck, lint, format:check — чисто.
- Все тесты зелёные: 264 теста в трёх пакетах.
- `pnpm build` — 6 пакетов.
- Smoke собранного API: `/health → {"status":"ok"}`.
- `docker compose config` для обоих файлов — синтаксис и подстановка
  переменных в порядке; наружу публикуются только 80 и 443.
- `check-prod-config.sh` — 23 пункта.
- Интерфейс — живым браузером через Playwright на локальном стенде.

**НЕ проверено — это главное, что нужно знать перед развёртыванием:**

- **`docker compose build --no-cache` ни разу не запускался.** Из песочницы,
  где писался код, egress-прокси отклоняет `registry-1.docker.io` по политике
  организации. Оба compose-файла падают на скачивании базового образа, до
  первой строки Dockerfile. **Первая настоящая сборка образов произойдёт на
  сервере.** Dockerfile'ы и entrypoint разбирались по частям, но целиком не
  прогонялись — закладывайтесь на то, что первая сборка может потребовать
  правок.
- **Caddyfile.prod не проверялся бинарником `caddy validate`** — его тоже
  неоткуда было взять.
- Сертификат Let's Encrypt не выпускался ни разу.
- Живые Google, Telegram и OpenAI не вызывались ни разу за всю работу.
  Все интеграции проверены только заглушками.
- Миграции применялись к тестовой и локальной базам, не к production.

## 7. Грабли, на которые уже наступали

Стоит держать в голове — они повторяются:

1. **Google Calendar API нужно включать отдельно.** 403 `accessNotConfigured`
   приложение раньше принимало за отзыв доступа. Починено, но саму галку в
   Cloud Console всё равно надо поставить.
2. **Стенд отдаёт старый бандл после пересборки.** Дважды приходилось
   перезаходить в аккаунт, чтобы увидеть изменения: виноват service worker
   PWA (`registerType: 'autoUpdate'`).
3. **Токены дизайна, которых нет.** Трижды находили правила, ссылающиеся на
   несуществующий CSS-токен `--ink`. Невалидный `var()` не откатывается к
   предыдущему значению — свойство получает начальное. Так пропадали модалка,
   ячейки карты касаний и заливка активного чипа. Если что-то выглядит
   «почти правильно» — проверьте `var(--` по всем стилям.
4. **`git am` на компьютере ловит блокировки.** Если MCP переподключался,
   разрешение на удаление файлов слетает, `git` не может убрать `.git/HEAD.lock`
   и патчи ложатся наполовину.
5. **`allowBuilds` в `pnpm-workspace.yaml`** — несуществующий ключ, pnpm его
   молча игнорирует. Правильные: `onlyBuiltDependencies` и
   `ignoredBuiltDependencies`.

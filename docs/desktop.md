# Десктоп-обёртка (Tauri) — логика работы и взаимодействий

Как устроена и куда ходит desktop-версия «Траектории». Отдельного backend/UI
для десктопа нет — это обёртка вокруг того же `apps/web`, и учитывая, что
окружений всего два (локальный dev на localhost и прод на VPS, без стейджинга),
именно граница между ними — источник всех особенностей ниже.

---

## 1. Из чего состоит

```
apps/web      — тот же React SPA, что и в браузере. Один код, два способа его
                собрать (обычная веб-сборка и build:desktop).
apps/desktop  — тонкая Tauri-оболочка (Rust). Своего UI нет: main.rs просто
                поднимает окно и просит tauri.conf.json сказать, что в нём
                показывать.
apps/api      — тот же NestJS backend, что обслуживает браузерную версию.
                Десктоп не имеет своей копии API — ходит либо в dev-инстанс
                на localhost:3000, либо в прод на VPS.
```

Ключевая мысль: **desktop не самостоятельный сервис, а два разных способа
доставить один и тот же фронтенд** — либо через Vite dev-сервер (разработка),
либо вшитым в exe (готовая программа, смотрит на прод).

---

## 2. Два режима — и что с чем говорит в каждом

### 2.1 Dev-режим — `pnpm --filter @planner/desktop dev`

```
tauri dev
  → beforeDevCommand: pnpm --filter @planner/web dev   (Vite dev-сервер)
  → окно открывает devUrl = http://localhost:5173
```

Внутри окна работает обычный Vite dev-сервер с HMR. Запросы к `/api/*`
идут через прокси `apps/web/vite.config.ts` → `server.proxy['/api']`, который
перенаправляет их на `VITE_API_URL` (по умолчанию `http://localhost:3000`).
То есть браузер (WebView2) видит всё как один источник — `localhost:5173`,
прокси незаметно уносит `/api` на локальный `apps/api`. CORS тут ни при чём:
для WebView всё выглядит same-origin.

Нужен локально поднятый `apps/api` (обычный `pnpm --filter @planner/api dev`)
и Postgres — то есть то же самое окружение, что и для обычной веб-разработки.

### 2.2 Desktop-прод — `pnpm --filter @planner/desktop tauri:build`

```
tauri build
  → beforeBuildCommand: pnpm --filter @planner/web build:desktop
      (vite build --mode desktop, подхватывает apps/web/.env.desktop:
       VITE_API_URL=https://yourtrajectory.app)
  → frontendDist: apps/web/dist — вшивается в exe как статика
  → exe запускается локально, окно открывает embedded assets
```

Здесь всё иначе: собранный `dist` не деплоится никуда — он **физически
внутри exe**. Когда пользователь запускает программу, WebView2 отдаёт
страницу со служебного адреса `http://tauri.localhost` (это дефолт Tauri 2 на
Windows, если `useHttpsScheme` не включён — см. `tauri-utils` /
`config.rs`), а не с `yourtrajectory.app`.

Из этого вытекают все следующие пункты.

---

## 3. Почему это не «просто открыть сайт в окне»

Раз фронтенд физически не на домене, а на `http://tauri.localhost`, каждый
fetch к API — **кросс-доменный запрос**, хотя в браузере (при обычном заходе
на `yourtrajectory.app`) это был бы same-origin через Caddy. Отсюда три точки,
которые обязаны быть согласованы:

| Что                              | Где лежит                                                          | Зачем |
| -------------------------------- | ------------------------------------------------------------------- | ----- |
| Абсолютный адрес API              | `apps/web/.env.desktop` → `VITE_API_URL=https://yourtrajectory.app` | В браузере `BASE` пустой (`api/client.ts:41`) и относительные пути работают сами по себе через Caddy. В десктопе относительный путь резолвился бы в `http://tauri.localhost/api/...`, а такого сервера нет — значит нужен абсолютный адрес. |
| Разрешение в CSP                 | `apps/desktop/src-tauri/tauri.conf.json` → `app.security.csp.connect-src` | Без этого сам WebView2 заблокирует fetch на chужой домен ещё до сети — по своей же Content-Security-Policy. |
| Разрешение в CORS на сервере      | `apps/api/src/main.ts` → `cors.origin` включает `'http://tauri.localhost'` | Даже если фронтенд достучался, браузер (WebView2) не отдаст ответ JS-коду, пока сервер явно не разрешит именно этот Origin. Без этого — молчаливая сетевая ошибка, которую фронт интерпретирует как «сервер не настроен» (see `App.tsx`: `googleConfigured ?? false`). |

Важно: `http://tauri.localhost` — фиксированная константа самого Tauri
(зависит только от того, что `useHttpsScheme` не включён), а не что-то, что
меняется между машинами или сборками. Поэтому её можно разрешать в CORS
навсегда, не заводя отдельную переменную окружения на сервере: подделать
такой Origin с постороннего сайта нельзя.

## 4. Раздельная сборка веба: `build` vs `build:desktop`

`apps/web/package.json` держит два скрипта именно чтобы дев-домен не утёк
в обычный прод-деплой:

- `build` — обычная веб-сборка (её гоняет `docker-compose.prod.yml` для
  контейнера `web`). `.env.desktop` не читает, к десктопу отношения не имеет.
- `build:desktop` (`vite build --mode desktop`) — то же самое, но Vite
  подхватывает `.env.desktop` поверх обычного `.env*`. Использует его только
  `apps/desktop` через `beforeBuildCommand` в `tauri.conf.json`.

Итог: правки под десктоп не задевают обычный веб-деплой на VPS, и наоборот.

---

## 5. Service worker внутри desktop-сборки

`apps/web/vite.config.ts` включает `vite-plugin-pwa` с `registerType:
'autoUpdate'`. У WebView2 есть свой профиль (кеш, service worker, IndexedDB),
который **переживает пересборку exe** — в отличие от самого бинарника, он не
перезаписывается при каждом `tauri:build`. Из-за этого один раз
зарегистрированный SW может годами отдавать старый закэшированный бандл поверх
свежесобранного exe, и баг выглядит так, будто правка «не применилась», хотя
на самом деле применилась, просто SW её не показывает.

Поэтому для `mode === 'desktop'` в `vite.config.ts` включён `selfDestroying:
true` — вместо обычного кеширующего SW собирается «самоуничтожающийся»,
который при активации сносит и себя, и все свои кеши. Раз ассеты и так
физически внутри exe, офлайн-кеш десктопу не нужен вообще — SW там чистая
обуза с единственным реальным риском (застревание на старой версии).

## 6. Иконки — один источник на оба фронта

`apps/web/public/icons/icon-512.png` — общий мастер-файл. Иконки Windows/
macOS/Android/iOS в `apps/desktop/src-tauri/icons/*` сгенерированы из него
командой `pnpm exec tauri icon <путь-к-png-или-svg>` (запускается из
`apps/desktop`). Если мастер-иконку меняют — перегенерировать все размеры
одной командой, вручную ничего не подгонять.

Фавикон браузерной вкладки (`apps/web/public/favicon.svg`) — отдельный SVG-
файл с тем же изображением (три точки на тёмном фоне), но это независимая
копия: у SVG-фавикона нет автоматической синхронизации с PNG-мастером, при
смене дизайна нужно поправить оба места руками.

## 7. Что перестраивать при каких правках

| Что поменялось                                   | Что пересобирать |
| ------------------------------------------------- | ----------------- |
| `apps/api/**` (включая CORS, роуты, бизнес-логику) | Только прод-сервер: `git pull` + `docker compose ... up -d --build api`. Локальный `.exe` трогать не нужно — desktop лишь клиент API. |
| `apps/web/**` (UI, стили, клиентская логика)       | `.exe` нужно пересобрать (`pnpm --filter @planner/desktop tauri:build`), а если меняли и обычный прод-фронт — ещё и `web`-контейнер на сервере. |
| `apps/desktop/src-tauri/**` (конфиг Tauri, иконки, Rust) | Только `.exe`. |
| Иконки (`apps/web/public/icons/*`)                | И PWA-манифест (пересоберётся сам при следующей веб-сборке), и `.exe` (нужно вручную прогнать `tauri icon` + пересборка). |

## 8. Известные ограничения

- **MSI не собирается на этой машине.** `light.exe` из WiX3 требует .NET
  Framework 3.5, который по умолчанию выключен в Windows 10/11. Сам `.exe` в
  `target/release/traektoria.exe` от этого не страдает — это уже готовый
  самостоятельный бинарник, MSI лишь оборачивает его в инсталлятор.
- **macOS и Linux ни разу не собирались** — `tauri.conf.json` целится в
  Windows-специфичный `http://tauri.localhost`; на macOS/Linux дефолтная схема
  другая (`tauri://localhost` без порта), и CORS-разрешение на сервере
  придётся расширять под неё отдельно, если/когда дойдут руки собирать там.
- **Один production-домен.** Раз нет стейджинга, `.env.desktop` целится прямо
  в `yourtrajectory.app` — то есть desktop-сборка всегда говорит с боевыми
  данными, отдельного «песочница»-контура для десктопа нет.

# Траектория

Личный планировщик, построенный вокруг одного фокуса, а не вокруг списка обязательств.

Приложение отвечает на три вопроса: что действительно требует внимания сегодня, чем
я занимаюсь прямо сейчас и что лежит перед глазами. Всё остальное — направления,
проекты, книги, идеи — доступно, но не давит.

Интерактивный прототип, с которого начался проект, лежит в `docs/reference/app_2.html`
и остаётся визуальным референсом.

## Продуктовые принципы

- **Задача не существует без проекта.** Направление задачи всегда вычисляется через проект.
- **Одна активная задача на всё приложение.** Выбор новой снимает предыдущую — та просто
  остаётся обычной открытой задачей.
- **Направление в фокусе и активная задача не могут расходиться.** При попытке создать
  противоречие сервер возвращает 409, а интерфейс спрашивает, что делать.
- **Закрепление — это стикер, а не статус.** Закрепляется задача, но показывается всегда
  вместе с проектом: `проект → задача → направление`.
- **Никакого «бэклога».** Все незавершённые задачи проекта равноправны; отсутствие
  дедлайна не делает задачу задачей второго сорта.
- **Касания принадлежат направлению**, а не задаче, и считают факт работы, а не часы.
- **Напоминания — внешняя память.** Без проекта, без просрочки, с архивом на семь дней.

## Архитектура

```
Браузер / PWA / Tauri
        │  REST (JSON, Zod-контракты)
        ▼
   NestJS API ──────────────┐
   ├─ модули домена         │  Drizzle ORM
   ├─ планировщик доставки  ├──────────────► PostgreSQL
   └─ Telegram-бот (grammY) │
                            │
        общие application services: бот и HTTP API
        вызывают одни и те же сервисы
```

API, планировщик напоминаний и Telegram-бот пока живут в одном процессе NestJS, но
разделены по модулям: `RemindersModule` (доставка) и `TelegramModule` (бот) не знают
друг о друге напрямую — канал доставки подключается через `NotificationRouter`.
Это позволит вынести worker и бота в отдельные процессы без переписывания логики.

## Требования

- Node.js 20+ (проверялось на 22)
- pnpm 10 (`corepack enable`)
- PostgreSQL 16 — локально или через Docker
- Для десктопной сборки — Rust и системные зависимости Tauri (см. `apps/desktop/src-tauri/README.md`)

## Быстрый старт

```bash
corepack enable
pnpm install
cp .env.example .env            # одного файла в корне достаточно

# 1. база
docker compose up -d postgres   # или свой PostgreSQL

# 2. схема и демо-данные
pnpm db:migrate
pnpm db:seed

# 3. приложение
pnpm dev                        # API на :3000, веб на :5173
```

Открыть `http://localhost:5173`. Swagger — `http://localhost:3000/docs`.

`pnpm dev` поднимает API и веб параллельно. Отдельно: `pnpm dev:api`, `pnpm dev:web`.

### Переменные окружения

| Переменная             | Зачем                                                            |
| ---------------------- | ---------------------------------------------------------------- |
| `DATABASE_URL`         | строка подключения к PostgreSQL                                  |
| `PORT`                 | порт API, по умолчанию 3000                                      |
| `WEB_ORIGIN`           | источник для CORS, по умолчанию `http://localhost:5173`          |
| `TELEGRAM_BOT_TOKEN`   | токен бота; пусто — бот не стартует                              |
| `TELEGRAM_MODE`        | `polling` (dev), `webhook` (prod) или `off`                      |
| `TELEGRAM_WEBHOOK_URL` | публичный адрес вебхука для production                           |
| `DEV_USER_ID`          | UUID демонстрационного пользователя                              |
| `DEV_AUTH`             | `true` — все запросы от `DEV_USER_ID`; **только для разработки** |
| `APP_TIMEZONE`         | таймзона по умолчанию                                            |
| `VITE_API_URL`         | адрес API для фронтенда (в dev работает прокси Vite)             |

`.env` ищется вверх по дереву от текущей папки, поэтому одного файла в корне
монорепо хватает и для `pnpm dev`, и для `pnpm db:migrate`, который запускается
внутри `apps/api`. Локальный `apps/api/.env`, если он есть, перекрывает корневой.

### Про авторизацию

Вход — Google OAuth, серверный поток с кодом. Сессия живёт в httpOnly-куке
`traektoria_session`: в куке случайный токен, в базе только его SHA-256, так что
дамп базы не даёт войти под пользователем. Кука `SameSite=Lax`, в production
добавляется `Secure`. Срок — `SESSION_TTL_DAYS` (по умолчанию 30 дней).

Что нужно завести в Google Cloud Console:

1. Проект, в нём включить **Google Calendar API** (для входа отдельный API не нужен —
   имя и почта приходят в ID-токене).
2. **OAuth consent screen**, тип External. На этом шаге добавить только scopes
   `openid`, `userinfo.email`, `userinfo.profile`. Календарный scope сюда **не**
   добавлять: он запрашивается вторым, отдельным согласием. Пока приложение не
   верифицировано, себя добавить в Test users.
3. **Credentials → OAuth client ID → Web application**, redirect URI:

```
http://localhost:3000/api/auth/google/callback
http://localhost:3000/api/calendar/google/callback
http://localhost:8080/api/auth/google/callback
http://localhost:8080/api/calendar/google/callback
```

Первая пара — для `pnpm dev`, вторая — для docker-стенда, где Caddy проксирует
`/api`. Google сверяет URI побуквенно. Для боевого домена добавляются такие же
пути с `https://`.

Client ID и secret кладутся в `.env` на сервере. Во фронтенд они не попадают:
браузер уходит на `/api/auth/google`, всё остальное происходит на сервере.

Правила гварда:

- есть живая сессия → пользователь берётся из неё, заголовки игнорируются;
- сессии нет и `DEV_AUTH` включён → подставляется `DEV_USER_ID`, а заголовок
  `x-user-id` позволяет ходить от имени другого пользователя (нужно для тестов);
- сессии нет и `DEV_AUTH` выключен → 401;
- `NODE_ENV=production` + `DEV_AUTH=true` → приложение падает при старте;
- `NODE_ENV=production` без `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` или без
  `SESSION_SECRET` → тоже падает, чтобы не запуститься без настоящего входа.

Выход — `POST /api/auth/logout`: сессия удаляется из базы, кука очищается.
Неавторизованный пользователь видит экран входа вместо приложения.

## База данных и миграции

Схема описана в `apps/api/src/db/schema.ts`, миграции генерирует drizzle-kit:

- `0000_big_preak.sql` — базовая схема: пользователи, настройки, фокус, направления,
  проекты, задачи, чек-листы, касания, напоминания, доставки, входящие, меню, книги
  и фильмы, привязка Telegram;
- `0001_clever_sumo.sql` — календари и их события.

`pnpm db:seed` идемпотентен: повторный запуск ничего не дублирует (отметка в
`seed_markers`). Загружаются пять направлений, тринадцать проектов, тридцать одна
задача, около двухсот касаний за полгода, напоминания на сегодня, книги и фильмы,
меню и входящие.

## Напоминания

Планировщик (`@nestjs/schedule`) раз в 30 секунд ищет наступившие напоминания.
Redis не нужен:

1. считается момент доставки в таймзоне **пользователя**, а не браузера;
2. создаётся `reminder_delivery` с уникальным `idempotency_key`
   (`alert:<id>:<дата>:<время>`, `digest:<userId>:<дата>` или `evening:<userId>:<дата>`);
3. вставка идёт через `ON CONFLICT DO NOTHING`, затем условный `UPDATE ... WHERE
status = 'pending'` — так доставку забирает ровно один исполнитель;
4. неудача повторяется до трёх раз, затем доставка помечается `failed` с текстом ошибки.

Напоминания без точного времени собираются в одну дневную сводку на время из настроек.
В ту же сводку попадают задачи, у которых наступил `remindAt`.

**Пропущенное** (день напоминания уже прошёл) обрабатывается по `missedBehavior`
самого напоминания — планировщик не решает это за пользователя:

| Значение     | Поведение                                                    |
| ------------ | ------------------------------------------------------------ |
| `none`       | не догонять вообще: ни сводкой, ни вечером                   |
| `nextDigest` | попадёт в ближайшую утреннюю сводку                          |
| `evening`    | придёт отдельным вечерним сообщением в 20:00 по пользователю |

Для задач с `remindAt` берётся значение по умолчанию из настроек пользователя.
Перенос «через час» в 23:30 уезжает на завтра, а не в прошлое; «вечером» после 20:00 —
на завтрашний вечер.

Если `TELEGRAM_BOT_TOKEN` не задан, работает **mock-канал**: сообщение пишется в лог с
пометкой `[MOCK-ДОСТАВКА]`, доставка считается обработанной.

## Telegram-бот

```bash
TELEGRAM_BOT_TOKEN=... TELEGRAM_MODE=polling pnpm dev:api
```

### Связывание аккаунта

Чат Telegram связывается с аккаунтом «Траектории» одноразовым кодом — так
привязка достаётся тому, кто её запросил, а не первому написавшему боту:

1. в «Настройках» нажать **Подключить Telegram**;
2. сервер выдаёт код из 8 символов, действующий 15 минут; предыдущие
   невыданные коды при этом гасятся, чтобы на руках был ровно один;
3. пользователь отправляет боту `/start <код>` (или открывает готовую ссылку,
   если задан `TELEGRAM_BOT_USERNAME`);
4. сервер погашает код одним условным `UPDATE` и связывает
   `telegramUserId`/`chatId` с этим аккаунтом;
5. повторно тот же код не сработает;
6. в настройках видно состояние подключения, есть «Отключить» и «Подключить
   заново».

Автоматическая привязка первого написавшего к seed-пользователю осталась
только для локальной разработки и включается вместе с `DEV_AUTH`, а не по
`NODE_ENV`: там, где настроен настоящий вход, она не сработает.

## PWA

Сборка `pnpm --filter @planner/web build` генерирует манифест и service worker.
Кешируется только оболочка приложения; запросы к `/api` идут по стратегии `NetworkOnly` —
показывать вчерашний дедлайн как сегодняшний опаснее, чем показать ошибку сети.
Для офлайна есть `public/offline.html`.

**Установка в Chrome или Edge:** откройте приложение по HTTPS (или на `localhost`),
нажмите значок установки в адресной строке либо меню ⋮ → «Установить приложение».
После установки оно откроется отдельным окном без вкладок браузера.

## Десктоп (Tauri 2)

Конфигурация в `apps/desktop/src-tauri`. Отдельного интерфейса нет: в dev открывается
`http://localhost:5173`, в production упаковывается `apps/web/dist`. Выданы только
базовые права окна — доступа к файловой системе и оболочке нет.

Иконки лежат в `apps/desktop/src-tauri/icons` (сгенерированы `tauri icon` из
`icons/source.png`). Скрипт `pnpm --filter @planner/desktop build` проверяет наличие
Rust: если `cargo` не найден, шаг честно помечается пропущенным и общая сборка
монорепо не падает. Полная сборка — `pnpm --filter @planner/desktop tauri:build`.

**Проверено:** сборка прошла целиком на Linux (`Траектория_0.1.0_amd64.deb`).
Конфигурация, иконки, `frontendDist` и capabilities валидны. На Windows нужны
Rust и WebView2; сборка под Windows и macOS ещё не запускалась.

## Docker

```bash
docker compose up -d          # postgres + api + web (Caddy на :8080)
docker compose up -d postgres # только база — удобно для локальной разработки
```

У всех трёх сервисов настроены healthcheck. Секреты в репозиторий не попадают:
`TELEGRAM_BOT_TOKEN` и прочее подставляются из окружения.

Compose-стенд намеренно поднимается в **dev-режиме** (`NODE_ENV=development`,
`DEV_AUTH=true`): настоящей авторизации ещё нет, а с `DEV_AUTH=false` весь интерфейс
получал бы 401. Это локальный демо-стенд, не боевой запуск.

**Не проверено:** Docker в среде разработки отсутствовал, поэтому образы не собирались.
Compose-файл и Dockerfile написаны, но их стоит прогнать локально.

## Тесты

```bash
pnpm test
```

- `packages/shared` — 22 теста: разбор относительных дат («завтра», «в субботу»,
  «через две недели», «3 сентября»), арифметика дат и таймзон, recurrence, склонения.
- `apps/api` — 55 тестов на реальной PostgreSQL: вертикальный срез
  (направление → проект → задача → активная → закрепление → выполнение), конфликт
  фокуса, фильтры задач, касания, напоминания, архив за семь дней, входящие,
  книги, единый формат ошибок; доставка напоминаний, защита от повторной отправки,
  дневная сводка и ретраи; поведение при пропуске (`missedBehavior`); переносы
  напоминаний; напоминания по задачам; гвард авторизации; проверки владения
  (чужое направление, чужой проект, завершённый проект); диалог телеграм-бота.
- `apps/web` — 11 тестов: связка «направление → проект → задача», отсутствие дубля
  активной задачи в закреплённом, состояние «без фокуса», закрепление и открепление,
  диалог конфликта фокуса со страницы направления, свёрнутый хвост просроченного.

Файлы тестов API идут строго по очереди (`fileParallelism: false`): они делят одну
базу и чистят её перед прогоном.

Отдельно — дымовая проверка собранного приложения:

```bash
pnpm --filter @planner/api build
pnpm --filter @planner/api smoke:dist
```

Она нужна потому, что `pnpm dev` и тесты идут через tsx, а он не эмитит
`design:paramtypes`. Собранный `tsc`-ом код ведёт себя иначе: Nest видит
метаданные и пытается внедрять зависимости по типам. Приложение может падать
на старте, оставаясь зелёным во всех тестах, — поэтому конструкторы провайдеров
и гвардов должны либо иметь явный `@Inject(TOKEN)` у каждого параметра, либо
не иметь параметров вовсе.

Тестам API нужна база `planner_test`:

```bash
createdb planner_test   # или TEST_DATABASE_URL=postgres://...
```

## Что осталось моковым

- **Календари.** Таблицы и события есть, интерфейс показывает их в блоке «Сегодня»,
  но синхронизации с Google Calendar и Яндекс Календарём нет — нужен OAuth и бэкенд.
- **ИИ-разбор входящих.** Работает `MockAiProvider` на детерминированных правилах.
  Интерфейс `AiProvider` готов к подключению настоящей модели; дату он не выдумывает
  и при её отсутствии оставляет поле пустым.
- **Авторизация.** Dev-guard вместо настоящего провайдера.
- **Push-уведомления.** Веб-пуши не подключены; доставка идёт в Telegram или в лог.
- **Экспорт данных.** Кнопка обозначена как будущая функция.
